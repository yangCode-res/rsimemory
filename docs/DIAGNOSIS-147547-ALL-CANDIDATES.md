## 已确认的共同检索缺陷

三个生成策略的分词函数都使用空白切分的词/词组，替换了基线适用于中文的字符二元组。中文通常没有词间空格，完整问题词与历史记录中的局部事实无法匹配，词面分数大量归零。随后按会话新旧排序，同分记录偏向当前会话，排掉了大量较早的相关事实。候选 3 还在词面初筛后的 10 条内重排，不能找回未入池的历史记录。

在四位验证患者各自第 5 个检查点的全部 36 题上，固定每个候选实际使用的首次成功 search 输入、过滤条件和可见历史，仅修改分词函数：

|---|---:|---:|---:|---:|
|候选 1，缓存方向|8/36，22.22%|18/36，50.00%|18/36，50.00%|24/36 → 0/36|
|候选 2，近期加权方向|8/36，22.22%|19/36，52.78%|18/36，50.00%|24/36 → 0/36|
|候选 3，重排方向|8/36，22.22%|18/36，50.00%|18/36，50.00%|24/36 → 0/36|

候选 1、2 的原控制组均 36/36 完全复现原首次检索 ID 和顺序。候选 1 修复分词后的 top-5 与基线在 36/36 题上完全一致；候选 2 为 14/36，其近期加权仍改变排序。候选 2 的近期权重默认 0.2，在分词修复对照中保留，因此主要恢复不依赖关闭该新机制。不能仅凭小样本的一道额外命中宣称该机制提升最终准确率。

候选 3 复用 2026-10-17 的已留档对照，原控制组为 34/36 完全复现；在这 34 道严格匹配题上，恢复分词也将命中由 8/34 提升为 16/34，等于同输入基线。单独关闭候选 3 的重排不能恢复召回。详情见 `DIAGNOSIS-147547-CANDIDATE3.md`。

## 上游工程缺陷：父版本代码缺少依赖

运行冻结的 `095e7f1` 代码和实际轨迹共同证实：`rsi/cli.py` 使用 `root_code=inspect.getsource(PlainPolicy)`，仅提取类定义，未携带模块级 `_grams` 及 imports。

原始 `diagnostic-input` 和三个 `llm.codegen` 请求均有如下特征：

- 父代码长 9072 字符，包含 `PlainPolicy` 类。
- `_grams` 被调用 2 次，定义数量为 0。
- 没有模块 imports，也没有声明字符二元组分词行为。

因此生成输入没有提供完整的父策略实现，模型需要自行补齐缺失依赖；三个候选均补成了不适合本次中文数据的空白分词。这是父版本打包的工程缺陷。缺失依赖与错误补全均已观测；尚未进行“完整父代码重新生成”的对照，不能断言缺失依赖是错误分词的唯一生成诱因。
